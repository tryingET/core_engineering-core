# engineering-core v0.12.0 fleet rollout

## Why

44 repos pin engineering-core v0.7.0–v0.10.0 (39 on v0.7.0). Lane fixes shipped in v0.11.0–v0.12.0 reach a repo only when it moves its pin, so today almost no repo has them. Most pins also use `git+file:///home/tryinget/...`, a path that exists only on this workstation.

## Target pin (exact)

Every repo ends with this in `policy/engineering-lane.json` under `engineering_core` (keep all other keys it already has):

```json
"repository": "https://github.com/tryingET/core_engineering-core",
"ref": "v0.12.0",
"release_pin": {
  "kind": "git-commit",
  "ref": "v0.12.0",
  "resolved_commit": "3fc8387274dddccbae3d7fab80954ad483c9b681",
  "source": "git+https://github.com/tryingET/core_engineering-core.git@3fc8387274dddccbae3d7fab80954ad483c9b681"
}
```

and every `*_command` / `command` value uses that `source` (`uv tool -n run --from 'git+https://github.com/tryingET/core_engineering-core.git@3fc8387274dddccbae3d7fab80954ad483c9b681' engineering-core ...`), never `git+file`. Update the release-pin line in `docs/engineering.local.md` to `v0.12.0` (`3fc8387274dddccbae3d7fab80954ad483c9b681`).

Don't use `engineering-core migrate` to move the pin: in the released v0.12.0 it ignores `--ref` when a `release_pin` exists (it only reorders keys). Edit the pin directly. (Fixed on `main` by AK6055 with `--ref-commit`; it ships in the next release.)

Guidance for the new version: `uv tool -n run --from 'git+https://github.com/tryingET/core_engineering-core.git@3fc8387274dddccbae3d7fab80954ad483c9b681' engineering-core show <lane>` (and `show-discipline <id>`). Read `CHANGELOG.md` sections 0.8.0–0.12.0 in `~/ai-society/core/engineering-core` for what changed.

## Per-repo procedure

Do one repo at a time. Never batch commits across repos.

1. **Preflight; skip rather than collide.** In the repo: `git status --short --branch`, `git fetch`. Skip the repo (report why) if any of these hold: files you'd touch are already modified; the branch is behind its upstream and can't fast-forward cleanly; another agent is visibly active (a commit in the last hour you didn't make, or a live process with the repo as its working directory: `for p in $(pgrep -f .); do readlink /proc/$p/cwd; done | grep <repo>`). Don't stash, reset, or delete anyone's files or locks.
2. **Baseline.** Read the repo's `AGENTS.md`, `docs/engineering.local.md`, and `policy/engineering-lane.json`. Run the repo's own gate (`just check`, `just ci`, or what AGENTS.md names) and record the result before changing anything. Pre-existing failures are baseline, not yours to fix.
3. **Move the pin** exactly as above.
4. **Adopt lane changes that apply**, only where the repo follows the lane default; where it deliberately differs, record the deviation in `docs/engineering.local.md` instead of forcing the lane. Most relevant, by lane:
   - **all Python repos:** `pyproject.toml` must declare `[tool.uv]` `exclude-newer = "7 days"` if its `uv.lock` records `exclude-newer-span` (many already got this in AK5998); never add `[tool.uv.scripts]` (uv ignores it and drops all other project `[tool.uv]` settings). Python ≥3.13 is the engineering-core floor, not a requirement for the consumer.
   - **ts / pi-ts:** TypeScript 7 only: typecheck with `tsc --noEmit` from exactly pinned `typescript@7`; replace `@typescript/native-preview`/`tsgo` and drop a `typecheck:fallback`. Biome config in 2.x shape (`biome migrate --write`), `complexity/useLiteralKeys` off when `noPropertyAccessFromIndexSignature` is on. Bun config file is `bunfig.toml` (a `bun.toml` is ignored). If a tool in the repo imports the classic TypeScript compiler API (`import ts from "typescript"` with `createProgram` etc.), don't upgrade it here: record it and move on (see AK5929 for the pattern).
   - **rust:** cargo gates use `--workspace --locked`; `cargo fmt --all --check` as the gate; pin the toolchain in `rust-toolchain.toml`.
   - **go:** format gate must fail (`gofmt -l`), `go mod tidy -diff && go mod verify`.
   - **cpp / elixir / common-lisp:** see the lane's Quality gates block.
   Keep lane adoption proportionate: a pin move plus the defects that actually affect this repo, not a rewrite.
5. **Validate.** Rerun the repo's gate. It must be no worse than baseline (same or fewer failures, none new). Run `uv run --project ~/ai-society/core/engineering-core engineering-core scan-adoption --scope <repo> --include-scope-root --format json --prefer-repo` and confirm `ref` is `v0.12.0` and there's no `uv_lock_records_undeclared_setting` flag.
6. **Commit** with explicit paths only (`git commit -- <paths>`), normal hooks (never `--no-verify`), message `chore(engineering-core): adopt v0.12.0 (AK<your task>)` plus a body listing what changed and any recorded deviation.
7. **Push** only if every unpushed commit on the branch is yours and the branch fast-forwards; otherwise leave it committed locally and report it.

## Stop and report instead of guessing

- A migration step would need a product decision (e.g. replacing a dev tool, changing a public package name).
- The repo's gate gets worse and the cause isn't obvious within a short investigation.
- A quiet-window request arrives from another session: stop AK/heavy work until its RELEASE.
